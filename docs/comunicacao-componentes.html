6.1 Objetivos da aula

Ao final desta aula, o(a) aluno(a) deve ser capaz de:

  1. Decompor uma interface em uma hierarquia de componentes e montá-la por composição (inclusive com a prop especial children).
  2. Passar dados de um componente pai para um filho com props, entendendo que props são somente leitura e que o fluxo de dados em React é unidirecional.
  3. Permitir que um filho avise o pai de um evento, passando funções como props (callbacks).
  4. Fazer dois componentes irmãos se comunicarem, elevando o estado (lifting state up) para o ancestral comum mais próximo.
  5. Identificar o problema do prop drilling e resolvê-lo com a Context API (createContext, Provider e useContext).
  6. Explicar o ciclo de vida de um componente funcional (montagem, atualização e desmontagem) e controlá-lo com useEffect e sua função de limpeza.
  7. Usar setTimeout e setInterval dentro de efeitos sem vazamentos, em casos reais: notificação que some sozinha, contagem regressiva e busca com atraso (debounce).

Por que este capítulo? O Projeto 1 exige comunicação entre componentes com Context API ou Redux e uma aplicação integrada, e não um conjunto de telas soltas. Este capítulo mostra todas as formas de comunicação, para que o grupo saiba quando usar cada uma.

6.3 1. Componentes compostos por outros componentes

6.3.1 Pensando em React: da tela à árvore de componentes

A documentação oficial propõe um roteiro de cinco passos para construir interfaces, chamado Thinking in React. Os dois primeiros tratam justamente da composição:

  1. Quebrar a interface em uma hierarquia de componentes. Desenhe caixas ao redor de cada parte da tela e dê um nome a cada uma. Use o princípio da responsabilidade única: idealmente, um componente faz uma coisa só; se ele cresce demais, deve ser dividido em subcomponentes.
  2. Construir uma versão estática. Escreva os componentes sem estado, apenas recebendo dados por props e renderizando-os. Nas palavras da documentação: construir a versão estática exige muita digitação e pouco raciocínio; adicionar interatividade exige muito raciocínio e pouca digitação.

6.3.3 Versão estática: compondo componentes

// src/components/CardVeiculo.jsx — composto por três subcomponentes
function FotoVeiculo({ src, alt }) {
  return <img src={src} alt={alt} className="card-img-top" />;
}

function InfoVeiculo({ modelo, marca, preco }) {
  return (
    <div className="card-body">
      <h5 className="card-title">{modelo}</h5>
      <p className="card-subtitle text-muted">{marca}</p>
      <p className="fw-bold mt-2">{preco.toLocaleString('pt-BR', { style: 'currency', currency: 'BRL' })}</p>
    </div>
  );
}

function BotaoFavorito() {
  return <button className="btn btn-outline-warning m-3">☆ Favoritar</button>;
}

function CardVeiculo({ veiculo }) {
  return (
    <div className="card h-100">
      <FotoVeiculo src={veiculo.foto} alt={veiculo.modelo} />
      <InfoVeiculo modelo={veiculo.modelo} marca={veiculo.marca} preco={veiculo.preco} />
      <BotaoFavorito />
    </div>
  );
}

export default CardVeiculo;

Repare que CardVeiculo não sabe como uma foto é desenhada nem como o preço é formatado: ele delega essas tarefas aos filhos. Isso torna cada parte reutilizável e mais fácil de testar e de alterar.

6.3.4 Composição com children: componentes “moldura”

Às vezes um componente não sabe, de antemão, o que vai mostrar dentro dele: é o caso de painéis, cartões, modais e layouts. Para isso, React oferece a prop especial children: tudo o que for escrito entre a tag de abertura e a de fechamento é entregue ao componente nessa prop.

// src/components/Secao.jsx — uma "moldura" reutilizável
function Secao({ titulo, children }) {
  return (
    <section className="card my-4">
      <div className="card-header fw-bold">{titulo}</div>
      <div className="card-body">{children}</div>
    </section>
  );
}

export default Secao;
// Uso: o conteúdo entre <Secao> e </Secao> vira a prop children
<Secao titulo="Ofertas da semana">
  <p>Descontos de até 10% em seminovos.</p>
  <ContagemOferta segundosIniciais={90} />
</Secao>

<Secao titulo="Fale conosco">
  <FormContato />
</Secao>

O mesmo componente Secao embrulha conteúdos completamente diferentes. Essa é a forma recomendada de reaproveitar código em React: composição, e não herança de classes.

Composição também ajuda a evitar prop drilling. Se um componente intermediário só recebe uma prop para repassá-la a um filho, muitas vezes é melhor que ele receba o filho já pronto via children. Veremos o problema do prop drilling na Seção 6.6.

6.4 2. Props: comunicação de pai para filho

6.4.1 O que são props

Props (properties) são os dados que um componente pai entrega a um filho. Em JSX, elas se parecem com atributos HTML; dentro do filho, chegam reunidas em um único objeto, que é o primeiro parâmetro da função.

// PAI: passa as props como atributos
<InfoVeiculo modelo="Civic Si" marca="Honda" preco={189000} />
//            └── string ──┘ └─ string ─┘ └─ expressão JS entre { } ─┘

// FILHO: recebe um objeto { modelo, marca, preco }
function InfoVeiculo(props) {
  return <h5>{props.modelo} — {props.marca}</h5>;
}

// Forma mais comum: desestruturação direto no parâmetro
function InfoVeiculo({ modelo, marca, preco }) {
  return <h5>{modelo} — {marca}</h5>;
}
Table 6.3: O que pode ser passado como prop
Tipo de valor Exemplo no pai Observação
String modelo="Civic" Única forma que dispensa chaves.
Número / booleano preco={189000} emEstoque={true} emEstoque sozinho equivale a emEstoque={true}.
Objeto veiculo={veiculo} Comum para entidades vindas da API.
Array veiculos={lista} O filho costuma usar .map().
Função onSelecionar={handleSelecionar} Permite ao filho avisar o pai (ver abaixo).
JSX / componentes children, icone={<Estrela />} Base da composição.

6.4.2 Valores padrão e repasse de props

// Valor padrão: usado quando o pai não envia a prop (ou envia undefined)
function Selo({ texto = 'Novo', cor = 'success' }) {
  return <span className={`badge bg-${cor}`}>{texto}</span>;
}

<Selo />                          // "Novo", verde
<Selo texto="Seminovo" cor="secondary" />

// Repasse com spread: envia todas as propriedades do objeto como props
const veiculo = { modelo: 'Onix', marca: 'Chevrolet', preco: 89000 };
<InfoVeiculo {...veiculo} />      // equivale a modelo="Onix" marca="Chevrolet" preco={89000}

Use o spread com moderação: ele é prático, mas esconde quais props o filho realmente recebe.

6.4.3 Props são somente leitura e o fluxo é unidirecional

Um componente nunca deve alterar as próprias props. Elas pertencem ao pai: para o filho, são como os parâmetros de uma função pura.

// ❌ ERRADO — tentar alterar a prop
function InfoVeiculo({ veiculo }) {
  veiculo.preco = veiculo.preco * 0.9;   // altera o objeto do PAI sem o React saber!
  return <p>{veiculo.preco}</p>;
}

// ✅ CERTO — calcular um novo valor a partir da prop
function InfoVeiculo({ veiculo, desconto = 0 }) {
  const precoFinal = veiculo.preco * (1 - desconto);
  return <p>{precoFinal}</p>;
}

Esse é o princípio do fluxo de dados unidirecional (one-way data flow): os dados descem na árvore, do pai para os filhos. Quando o dado muda, quem o possui (o pai, no seu estado) o altera, e o React renderiza novamente o pai e os filhos com as props atualizadas.

Table 6.4: Props × estado (state)
Props Estado (useState)
Analogia Parâmetros de uma função Memória do componente
Quem define O componente pai O próprio componente
Pode ser alterado pelo componente? Não (somente leitura) Sim, apenas pela função set...
Mudança provoca nova renderização? Sim, quando o pai envia um valor novo Sim
Uso típico Configurar e alimentar o filho Guardar dados que mudam com a interação

6.4.4 Funções como props: o filho avisando o pai

Se o fluxo é só de cima para baixo, como um botão dentro do card informa ao pai que foi clicado? A resposta: o pai passa uma função como prop, e o filho chama essa função no momento certo. É o conceito de callback, revisado no material 03-revisao-callback-promise-async-ajax.

// FILHO: não sabe o que acontecerá; apenas chama a função recebida
function BotaoFavorito({ ativo, onAlternar }) {
  return (
    <button
      className={`btn ${ativo ? 'btn-warning' : 'btn-outline-warning'}`}
      onClick={onAlternar}
    >
      {ativo ? '★ Favorito' : '☆ Favoritar'}
    </button>
  );
}

// PAI: possui o estado e decide o que fazer quando o filho "avisa"
function CardVeiculo({ veiculo }) {
  const [favorito, setFavorito] = useState(false);

  return (
    <div className="card h-100">
      <InfoVeiculo {...veiculo} />
      <BotaoFavorito
        ativo={favorito}                              // dado: pai → filho
        onAlternar={() => setFavorito(!favorito)}     // evento: filho → pai
      />
    </div>
  );
}
  CardVeiculo  (estado: favorito)
      │   ▲
      │   │  onAlternar()  ← o filho CHAMA a função do pai
      ▼   │
  BotaoFavorito  (props: ativo, onAlternar)

Convenção de nomes: props que recebem funções de evento começam com on (onAlternar, onSelecionar, onTextoChange); as funções que as implementam no pai costumam começar com handle (handleAlternar). Assim como em onClick, fica claro que a prop é “o que fazer quando algo acontecer”.

Note que os dados continuam descendo: o pai continua dono de favorito. O filho só pede a mudança. É por isso que o React chama essa técnica de fluxo de dados inverso (inverse data flow), e ela é a base da próxima seção.

6.5 3. Props: comunicação de irmão para irmão

6.5.1 O problema

Dois componentes irmãos não enxergam um ao outro: BarraFiltro não pode passar props diretamente a ListaVeiculos, pois nenhum deles renderiza o outro. Mas a lista precisa saber o que foi digitado na barra para se filtrar.

6.5.2 A solução: elevar o estado (lifting state up)

O roteiro Thinking in React responde a isso nos passos 3, 4 e 5:

  • Passo 3 — Encontrar a representação mínima do estado. Pergunte, para cada dado: ele permanece igual o tempo todo? Vem do pai via props? Pode ser calculado a partir de outro estado ou prop? Se a resposta a qualquer uma for “sim”, não é estado.
  • Passo 4 — Decidir onde o estado mora. Liste todos os componentes que usam aquele estado, encontre o ancestral comum mais próximo deles e coloque o estado ali (ou acima).
  • Passo 5 — Adicionar o fluxo de dados inverso. O dono do estado passa aos filhos o valor e uma função para alterá-lo.

Checkbox “Em estoque” Sim Não Não Sim

// src/components/PainelVeiculos.jsx — o pai comum, dono do estado

function PainelVeiculos({ veiculos }) {

  const [texto, setTexto] = useState('');
  const [categoria, setCategoria] = useState('');
  const [soEmEstoque, setSoEmEstoque] = useState(false);

    (categoria === '' || v.categoria === categoria) &&

  );
}

Passo a passo do que acontece quando o usuário digita “civ”:

  1. O onChange do <input> em BarraFiltro chama onTextoChange("civ").
  2. onTextoChange é, na verdade, o setTexto de PainelVeiculos: o estado do pai muda.
  3. O React renderiza PainelVeiculos novamente; filtrados é recalculado com o novo texto.
  4. Os três irmãos recebem props novas: BarraFiltro mostra “civ” no campo, ResumoFiltro mostra “1 veículo(s)”, ListaVeiculos mostra só o Civic.

Componentes controlados × não controlados. BarraFiltro não tem estado próprio: ele é controlado pelo pai, que decide os valores exibidos. Componentes controlados são mais fáceis de coordenar entre si; componentes com estado local são mais simples de usar isoladamente. Ao elevar o estado, você transforma um componente não controlado em controlado.

6.5.5 Quando elevar estado deixa de ser suficiente

Elevar estado funciona muito bem para componentes próximos na árvore. Mas observe o ContadorFavoritos, no Header, e o BotaoFavorito, dentro de cada CardVeiculo: o ancestral comum deles é o App. Para que o botão altere o contador, a lista de favoritos teria de morar em App e descer por cinco níveis:

App (favoritos, alternarFavorito)
 ├── Header (favoritos)                       ← só repassa
 │    └── ContadorFavoritos (favoritos)       ← USA
 └── PainelVeiculos (favoritos, alternar...)  ← só repassa
      └── ListaVeiculos (favoritos, alternar...)  ← só repassa
           └── CardVeiculo (favoritos, alternar...)  ← só repassa
                └── BotaoFavorito (ativo, onAlternar) ← USA

Isso é o prop drilling (“perfuração de props”): vários componentes recebem props que não usam, só para repassá-las. O código fica verboso, frágil (renomear uma prop exige mexer em todos os níveis) e acoplado. A solução é a Context API.

6.6 4. Context API e o Provider

6.6.1 A ideia

A Context API permite que um componente forneça (provide) um valor a toda a subárvore abaixo dele, e que qualquer descendente, a qualquer profundidade, leia esse valor diretamente, sem passar pelos intermediários.

                <FavoritosProvider value={...}>    ← fornece
                         │
          ┌──────────────┴─────────────────┐
        Header                       PainelVeiculos      ← não recebem nada
          │                                │
   ContadorFavoritos  ◄── useContext    ListaVeiculos
                                           │
                                       CardVeiculo
                                           │
                                     BotaoFavorito  ◄── useContext

São três peças:

Table 6.6: As três peças da Context API
Peça Código Papel
Criar o contexto const MeuContexto = createContext(valorPadrao) Define um “canal” de comunicação. Fica fora de qualquer componente.
Fornecer o valor <MeuContexto.Provider value={...}>...</MeuContexto.Provider> Envolve a parte da árvore que terá acesso ao valor.
Consumir o valor const valor = useContext(MeuContexto) Lê o valor do Provider mais próximo acima na árvore.

6.6.2 Primeiro exemplo: tema claro/escuro

// src/contexts/TemaContext.jsx
import { createContext, useContext, useState } from 'react';

// 1. CRIAR — o valor padrão só é usado se não houver Provider acima
const TemaContext = createContext({ tema: 'claro', alternarTema: () => {} });

// 2. FORNECER — um componente que guarda o estado e o entrega via Provider
export function TemaProvider({ children }) {
  const [tema, setTema] = useState('claro');
  const alternarTema = () => setTema((t) => (t === 'claro' ? 'escuro' : 'claro'));

  return (
    <TemaContext.Provider value={{ tema, alternarTema }}>
      {children}
    </TemaContext.Provider>
  );
}

// 3. CONSUMIR — hook personalizado, para não importar o contexto em todo lugar
// eslint-disable-next-line react-refresh/only-export-components
export function useTema() {
  return useContext(TemaContext);
}
// Qualquer componente dentro do TemaProvider:
import { useTema } from '../contexts/TemaContext.jsx';

function BotaoTema() {
  const { tema, alternarTema } = useTema();
  return (
    <button className="btn btn-sm btn-outline-light" onClick={alternarTema}>
      {tema === 'claro' ? '🌙 Escuro' : '☀️ Claro'}
    </button>
  );
}

Observe o padrão: o Provider é um componente comum que tem estado (useState) e usa children (Seção 6.3) para envolver o resto da aplicação. Quando o estado muda, todos os componentes que chamam useTema() são renderizados de novo com o valor atualizado.

Novidade do React 19: a partir da versão 19, o próprio contexto pode ser usado como Provider — <TemaContext value={...}> — e o .Provider passa a ser opcional. Projetos criados hoje com Vite já usam React 19, mas a forma <TemaContext.Provider> continua funcionando e é a que aparece na maior parte dos materiais; por isso a mantemos neste capítulo.

6.6.3 Exemplo principal: favoritos da AutoStore

Vamos eliminar o prop drilling da seção anterior. O contexto guardará a lista de favoritos, a função para alternar um favorito e uma notificação que será exibida por alguns segundos (usada na Seção 6.7).

// src/contexts/FavoritosContext.jsx
import { createContext, useCallback, useContext, useMemo, useState } from 'react';

// (1) Criar o contexto. null como padrão permite detectar uso fora do Provider.
const FavoritosContext = createContext(null);

// (2) Provider: dono do estado compartilhado
export function FavoritosProvider({ children }) {
  const [favoritos, setFavoritos] = useState([]);       // array de ids
  const [notificacao, setNotificacao] = useState(null); // { id, texto } ou null

  const alternarFavorito = useCallback((veiculo) => {
    const jaEraFavorito = favoritos.includes(veiculo.id);

    setFavoritos(
      jaEraFavorito
        ? favoritos.filter((id) => id !== veiculo.id)   // remove
        : [...favoritos, veiculo.id],                   // adiciona (novo array!)
    );

    setNotificacao({
      id: Date.now(),  // id único: duas mensagens iguais seguidas ainda são "novas"
      texto: jaEraFavorito
        ? `${veiculo.modelo} foi removido dos favoritos.`
        : `${veiculo.modelo} foi adicionado aos favoritos.`,
    });
  }, [favoritos]);

  const ehFavorito = useCallback((id) => favoritos.includes(id), [favoritos]);

  const fecharNotificacao = useCallback(() => setNotificacao(null), []);

  // (3) useMemo: o objeto value só é recriado quando algo dentro dele muda
  const valor = useMemo(
    () => ({
      favoritos,
      total: favoritos.length,
      ehFavorito,
      alternarFavorito,
      notificacao,
      fecharNotificacao,
    }),
    [favoritos, ehFavorito, alternarFavorito, notificacao, fecharNotificacao],
  );

  return <FavoritosContext.Provider value={valor}>{children}</FavoritosContext.Provider>;
}

// (4) Hook personalizado com verificação de segurança
// eslint-disable-next-line react-refresh/only-export-components
export function useFavoritos() {
  const contexto = useContext(FavoritosContext);
  if (!contexto) {
    throw new Error('useFavoritos deve ser usado dentro de <FavoritosProvider>.');
  }
  return contexto;
}

Pontos de atenção:

  • Imutabilidade: [...favoritos, veiculo.id] e .filter(...) criam novos arrays. Usar favoritos.push(...) alteraria o array existente e o React não perceberia a mudança.
  • useCallback e useMemo: sem eles, a cada renderização do Provider seriam criadas novas funções e um novo objeto valor, e todos os consumidores renderizariam de novo, mesmo sem mudança real. Em aplicações pequenas a diferença é mínima, mas fecharNotificacao estável será importante para o useEffect da próxima seção.
  • Hook com verificação: se alguém usar useFavoritos() fora do Provider, recebe uma mensagem clara em vez de um erro confuso como Cannot read properties of null.

6.6.4 Vários contextos e Providers aninhados

Uma aplicação pode ter quantos contextos precisar, cada um com uma responsabilidade. Eles são simplesmente aninhados:

<TemaProvider>
  <UsuarioProvider>
    <FavoritosProvider>
      <App />
    </FavoritosProvider>
  </UsuarioProvider>
</TemaProvider>

Um componente lê sempre o Provider mais próximo acima dele. Isso permite até sobrescrever um valor em uma parte da árvore:

<TemaContext.Provider value={{ tema: 'escuro', alternarTema }}>
  <Pagina />                      {/* usa "escuro" */}
  <TemaContext.Provider value={{ tema: 'claro', alternarTema }}>
    <Rodape />                    {/* usa "claro": Provider mais próximo */}
  </TemaContext.Provider>
</TemaContext.Provider>

6.6.5 Quando usar (e quando não usar) Context

Table 6.7: Escolhendo a técnica de comunicação
Situação Técnica recomendada
Filho precisa de um dado do pai Props
Filho precisa avisar o pai de um evento Função via props (callback)
Irmãos próximos compartilham um dado Elevar o estado ao pai comum
Componente intermediário só repassa JSX Composição com children
Dado usado em muitos lugares distantes (tema, idioma, usuário logado, carrinho, favoritos) Context API
Estado global grande, com muitas regras de atualização, histórico, DevTools Context + useReducer (Capítulo 5) ou Redux (material 06.3-react-redux-intro)

Cuidados:

  • Context não substitui todas as props. Componentes que dependem de contexto ficam menos reutilizáveis e mais difíceis de testar isoladamente. Use props para o que é local.
  • Quando o value muda, todos os consumidores daquele contexto renderizam de novo. Prefira vários contextos pequenos (tema, favoritos, usuário) a um “contexto gigante” com tudo.

Para o Projeto 1: o critério “comunicação entre componentes com Context API ou Redux” exige pelo menos um contexto (ou store) efetivamente compartilhado por componentes diferentes, como ContadorFavoritos e BotaoFavorito neste exemplo. Um contexto usado por um único componente não demonstra comunicação.

6.7 5. useEffect: ciclo de vida e efeitos colaterais

6.7.1 Renderizar deve ser puro; efeitos ficam fora da renderização

O corpo de um componente deve ser um cálculo puro: dadas as mesmas props e o mesmo estado, devolve sempre o mesmo JSX, sem modificar nada fora dele. Mas aplicações reais precisam fazer coisas “fora do React”:

  • buscar dados de uma API (Capítulo 5);
  • iniciar e cancelar temporizadores (setTimeout, setInterval);
  • alterar o título da aba (document.title), ler/gravar no localStorage;
  • registrar ouvintes de eventos globais (window.addEventListener('resize', ...));
  • conectar a um WebSocket (material 15-WebSockets).

Essas ações são chamadas de efeitos colaterais (side effects). Elas não podem ficar no corpo do componente, porque ele é executado a cada renderização, possivelmente muitas vezes. Quando o efeito é consequência de um evento (clique, envio de formulário), ele vai no manipulador do evento. Quando ele deve acontecer porque o componente está na tela (ou porque um valor mudou), ele vai em um useEffect.

6.7.2 O ciclo de vida de um componente funcional

Todo componente passa por três fases:

   ┌────────────┐        ┌────────────────────────────┐        ┌──────────────┐
   │ MONTAGEM   │ ─────► │ ATUALIZAÇÃO (0..N vezes)   │ ─────► │ DESMONTAGEM  │
   │ (mount)    │        │ (update)                   │        │ (unmount)    │
   └────────────┘        └────────────────────────────┘        └──────────────┘
   aparece na tela       props ou estado mudaram →              sai da tela
   pela 1ª vez           nova renderização                      (condição falsa,
                                                                troca de página...)

Em cada renderização, o React segue sempre a mesma ordem:

  1. Render: executa a função do componente e obtém o JSX.
  2. Commit: atualiza o DOM real com as diferenças.
  3. Efeitos: só depois que a tela foi atualizada, executa os useEffect cujas dependências mudaram — antes, roda a limpeza do efeito anterior, se houver.

6.7.3 Anatomia do useEffect

useEffect(() => {
  // CORPO: executado DEPOIS da renderização
  // (montagem e, conforme as dependências, atualizações)

  return () => {
    // LIMPEZA (opcional): executada ANTES da próxima execução do efeito
    // e na DESMONTAGEM do componente
  };
}, [dependencias]);  // controla QUANDO o efeito roda de novo
Table 6.8: Dependências do useEffect e as fases do ciclo de vida
Forma Montagem Atualização Desmontagem (limpeza)
useEffect(fn) Executa Executa em toda renderização Executa
useEffect(fn, []) Executa Nunca Executa
useEffect(fn, [a, b]) Executa Executa quando a ou b mudam Executa

Antes dos hooks (React 16.8), o ciclo de vida era controlado por métodos de componentes de classe. Você ainda os encontrará em projetos antigos e na literatura. Como destaca Gholami, o useEffect concentra em uma única chamada o que antes exigia vários métodos separados:

Table 6.9: Métodos de ciclo de vida de classes × componentes funcionais
Componente de classe Equivalente em componente funcional
componentDidMount() useEffect(() => { ... }, [])
componentDidUpdate(prevProps, prevState) useEffect(() => { ... }, [dep1, dep2])
componentWillUnmount() A função de limpeza retornada pelo useEffect
shouldComponentUpdate() React.memo(Componente)
getDerivedStateFromProps() Calcular o valor durante a renderização (dado derivado, Seção 6.5)
this.state / this.setState() useState

Pense em sincronização, não em “momentos”. A documentação oficial recomenda uma mudança de mentalidade: em vez de “o que fazer quando montar / atualizar / desmontar”, pergunte “com que valores este efeito precisa ficar sincronizado?”. Esses valores são as dependências. O corpo inicia a sincronização; a limpeza a desfaz. O React cuida de chamar os dois na hora certa.

6.7.4 Observando o ciclo de vida no console

// src/components/MonitorCiclo.jsx — componente didático
import { useEffect, useState } from 'react';

function Monitor({ valor }) {
  console.log(`[render] valor = ${valor}`);

  useEffect(() => {
    console.log('[efeito []]   montou');
    return () => console.log('[limpeza []]  desmontou');
  }, []);

  useEffect(() => {
    console.log(`[efeito [valor]]  sincronizou com valor = ${valor}`);
    return () => console.log(`[limpeza [valor]] desfez valor = ${valor}`);
  }, [valor]);

  return <p>Valor atual: {valor}</p>;
}

function MonitorCiclo() {
  const [visivel, setVisivel] = useState(true);
  const [valor, setValor] = useState(1);

  return (
    <div className="card card-body">
      <div className="btn-group mb-2">
        <button className="btn btn-primary" onClick={() => setValor(valor + 1)}>Incrementar</button>
        <button className="btn btn-secondary" onClick={() => setVisivel(!visivel)}>
          {visivel ? 'Desmontar' : 'Montar'}
        </button>
      </div>
      {visivel && <Monitor valor={valor} />}
    </div>
  );
}

export default MonitorCiclo;
Table 6.10: Saída do console (em produção, sem o StrictMode)
Ação Saída no console Fase
Página abre [render] valor = 1 → [efeito []] montou → [efeito [valor]] sincronizou com valor = 1 Montagem
Clique em Incrementar [render] valor = 2 → [limpeza [valor]] desfez valor = 1 → [efeito [valor]] sincronizou com valor = 2 Atualização
Clique em Desmontar [limpeza []] desmontou → [limpeza [valor]] desfez valor = 2 Desmontagem
Clique em Montar Igual à primeira linha, mas com o valor atual Nova montagem (estado do Monitor recomeça)

Observe três fatos importantes:

  1. O render sempre vem antes do efeito.
  2. Na atualização, a limpeza que roda é a do efeito anterior — ela ainda “vê” o valor antigo (1).
  3. O efeito com [] não roda na atualização, só na montagem e na desmontagem.

Por que tudo aparece duas vezes em desenvolvimento? O <StrictMode> do main.jsx monta, desmonta e monta de novo cada componente na primeira vez. É um teste proposital: se o seu efeito não tiver uma limpeza correta, o problema aparece já no desenvolvimento (por exemplo, dois temporizadores rodando ao mesmo tempo). Em produção (npm run build), isso não acontece.

6.7.5 Efeito simples: sincronizando o título da aba

// Dentro de ContadorFavoritos
const { total } = useFavoritos();

useEffect(() => {
  document.title = total > 0 ? `(${total}) AutoStore` : 'AutoStore';
}, [total]);   // sincroniza o título sempre que o total mudar

Aqui não há limpeza, porque não há nada a “desfazer”: a próxima execução simplesmente sobrescreve o título.

6.7.6 setTimeout em um efeito: notificação que some sozinha

Lembrando a revisão de callbacks: setTimeout(funcao, ms) agenda funcao para ser executada uma vez, após pelo menos ms milissegundos, e devolve um identificador numérico. clearTimeout(id) cancela o agendamento, se ele ainda não tiver acontecido.

Queremos que a mensagem do FavoritosContext apareça por 3 segundos e depois desapareça:

// src/components/Notificacao.jsx
import { useEffect } from 'react';
import { useFavoritos } from '../contexts/FavoritosContext.jsx';

function Notificacao({ duracao = 3000 }) {
  const { notificacao, fecharNotificacao } = useFavoritos();

  useEffect(() => {
    if (!notificacao) return;                          // nada a agendar

    const idTimer = setTimeout(fecharNotificacao, duracao);   // agenda o fechamento

    return () => clearTimeout(idTimer);                // LIMPEZA: cancela o agendamento
  }, [notificacao, fecharNotificacao, duracao]);

  if (!notificacao) return null;

  return (
    <div className="toast show position-fixed bottom-0 end-0 m-3" role="status">
      <div className="toast-body d-flex justify-content-between align-items-center gap-3">
        {notificacao.texto}
        <button className="btn-close" aria-label="Fechar" onClick={fecharNotificacao} />
      </div>
    </div>
  );
}

export default Notificacao;

Por que a limpeza é indispensável? Imagine que o usuário favorita o Civic e, um segundo depois, favorita o Corolla:

Table 6.11: O que acontece com e sem clearTimeout
Tempo Sem limpeza Com limpeza
0 s Mensagem “Civic…” aparece; timer A agendado para 3 s Igual
1 s Mensagem “Corolla…” aparece; timer B agendado para 4 s Antes de agendar B, a limpeza cancela o timer A
3 s Timer A dispara e fecha a mensagem do Corolla após só 2 s ❌ Nada acontece
4 s Timer B dispara (sem efeito, já estava fechada) Timer B fecha a mensagem do Corolla após 3 s ✅

Além disso, se o componente for desmontado (o usuário muda de página, por exemplo), sem a limpeza o timer continuaria agendado e executaria código referente a um componente que não existe mais.

Por que fecharNotificacao está nas dependências? Toda variável vinda de props, estado ou contexto usada dentro do efeito deve estar no array de dependências (o linter react-hooks/exhaustive-deps avisa quando falta alguma). Como ela foi criada com useCallback(..., []) no contexto, sua referência não muda, e o efeito não é reiniciado à toa. Sem o useCallback, cada renderização do Provider criaria uma nova função, reiniciando o timer e prolongando a notificação.

6.7.7 Contagem regressiva com setInterval

setInterval(funcao, ms) executa funcao repetidamente, a cada ms milissegundos, até ser cancelado com clearInterval(id). Vamos criar a oferta “termina em 01:30”:

// src/components/ContagemOferta.jsx
import { useEffect, useState } from 'react';

function ContagemOferta({ segundosIniciais = 90 }) {
  const [restantes, setRestantes] = useState(segundosIniciais);
  const encerrada = restantes <= 0;          // dado derivado

  useEffect(() => {
    if (encerrada) return;                   // não cria intervalo se já acabou

    const idIntervalo = setInterval(() => {
      // Atualização FUNCIONAL: usa sempre o valor mais recente do estado
      setRestantes((atual) => atual - 1);
    }, 1000);

    return () => clearInterval(idIntervalo); // para o relógio ao desmontar ou ao encerrar
  }, [encerrada]);

  const mm = String(Math.floor(Math.max(restantes, 0) / 60)).padStart(2, '0');
  const ss = String(Math.max(restantes, 0) % 60).padStart(2, '0');

  return encerrada
    ? <p className="text-danger fw-bold">Oferta encerrada.</p>
    : <p className="fw-bold">Oferta termina em <span className="font-monospace">{mm}:{ss}</span></p>;
}

export default ContagemOferta;

O efeito depende apenas de encerrada: ele cria um intervalo na montagem e só roda de novo quando a contagem chega a zero — e aí a limpeza para o relógio.

A armadilha do valor “congelado” (stale closure):

// ❌ ERRADO — a contagem para em 89
useEffect(() => {
  const id = setInterval(() => {
    setRestantes(restantes - 1);   // "restantes" é SEMPRE 90 aqui dentro!
  }, 1000);
  return () => clearInterval(id);
}, []);

Com [], o efeito roda uma única vez, e a função passada ao setInterval “captura” o valor de restantes daquela renderização (90). A cada segundo, ela calcula 90 - 1 de novo. A correção é a atualização funcional setRestantes((atual) => atual - 1), que recebe sempre o valor mais recente do React.

6.7.8 Busca com atraso (debounce) usando setTimeout

Na BarraFiltro da Seção 6.5, cada tecla filtra a lista imediatamente. Se o filtro disparasse uma requisição à API, digitar “corolla” geraria sete requisições. A técnica de debounce espera o usuário parar de digitar por um tempo antes de agir — e é feita com setTimeout + limpeza:

// src/components/CampoBusca.jsx — guarda o texto localmente e avisa o pai com atraso
import { useEffect, useState } from 'react';

function CampoBusca({ onBuscar, atraso = 500 }) {
  const [texto, setTexto] = useState('');   // estado LOCAL: atualiza a cada tecla

  useEffect(() => {
    const id = setTimeout(() => onBuscar(texto.trim()), atraso);
    return () => clearTimeout(id);          // nova tecla → cancela o agendamento anterior
  }, [texto, onBuscar, atraso]);

  return (
    <input
      className="form-control"
      placeholder="Buscar modelo..."
      value={texto}
      onChange={(e) => setTexto(e.target.value)}
    />
  );
}

export default CampoBusca;
Digitação:   c    o    r    o    l    l    a  ........ (pausa de 500 ms)
Timers:      ×    ×    ×    ×    ×    ×    ✓ → onBuscar("corolla")   (uma única chamada)
             └ cada nova tecla executa a limpeza, cancelando o timer anterior

No pai, basta usar <CampoBusca onBuscar={setTexto} />. A função setTexto do useState é estável (nunca muda), então não reinicia o efeito. Repare como as técnicas se combinam: o filho tem estado local para a digitação e usa um callback para comunicar ao pai só o valor final, que é então repassado ao irmão ListaVeiculos.

6.7.9 Você talvez não precise de um efeito

Efeitos são para sincronizar com sistemas externos. Usá-los para cálculos internos gera renderizações extras e erros sutis:

Table 6.12: Situações em que useEffect não é a ferramenta certa
Em vez de… Faça…
useEffect(() => setFiltrados(veiculos.filter(...)), [veiculos, texto]) Calcular const filtrados = veiculos.filter(...) na renderização.
useEffect que observa um estado para reagir a um clique Colocar a lógica diretamente no onClick / onSubmit.
useEffect para “avisar o pai” sempre que um estado local mudar Chamar o callback do pai no próprio manipulador do evento (exceção: atrasos como o debounce).
useEffect para copiar uma prop para o estado Usar a prop diretamente.
